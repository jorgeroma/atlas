El problema: infraestructura hecha a mano

  
Imagina que montas un entorno en la consola de AWS: una red, dos subredes, un balanceador, tres servidores y una base de datos. Funciona. Seis meses después te piden un entorno idéntico para pruebas. Nadie recuerda qué casillas se marcaron, qué puerto se abrió “un momento” para depurar ni por qué la base de datos tiene ese tamaño.

  
    
    
  • No es reproducible: cada entorno se parece al anterior, pero no es igual.
    • 
    
  • No hay historial: no sabes quién cambió qué, cuándo ni por qué.
    • 
    
  • No hay revisión: un cambio en producción no pasa por ningún pull request.
    • 
    
  • Deriva: la realidad se aleja de la documentación desde el primer día.
    • 
  


  
La solución: describir la infraestructura en ficheros

  
Infraestructura como código (IaC) significa que la infraestructura se define en ficheros de texto que viven en git, se revisan en pull requests y se aplican con una herramienta. Terraform es la herramienta de IaC más usada para esto, y funciona con casi cualquier plataforma que tenga API: AWS, Azure, Google Cloud, Kubernetes, GitHub, Cloudflare, Datadog y miles más.

  

    


    

    


    

  

  
Esta es la idea central de todo el curso. En un enfoque imperativo escribes los pasos. En uno declarativo escribes el estado final que quieres, y la herramienta calcula los pasos necesarios para llegar desde donde estás. Por eso Terraform es idempotente: si la realidad ya coincide con el código, no hace nada.


  
Cómo funciona Terraform por dentro

  

    
  

  
    
    
  • Terraform Core es el binario terraform. Lee tus ficheros, construye un grafo de dependencias, compara lo que quieres con lo que existe y decide qué crear, cambiar o borrar. No sabe nada de AWS ni de Azure.
    • 
    
  • Providers son plugins que traducen recursos a llamadas de API. hashicorp/aws sabe crear una instancia EC2; integrations/github sabe crear un repositorio. Se descargan del Terraform Registry.
    • 
    
  • State es un fichero JSON donde Terraform apunta qué objeto real corresponde a cada recurso de tu código (por ejemplo, que aws_instance.web es i-0b7d4e19a2). Sin él, Terraform no sabría qué gestiona. Tiene un bloque entero dedicado (07).
    •

Multi-nube, nube híbrida y cualquier servicio con API

  
Como Core no sabe nada de ninguna plataforma, el mismo flujo (escribir, plan, apply) y el mismo lenguaje sirven para todo lo que tenga un provider. Eso es lo que el examen llama gestionar flujos multi-cloud, hybrid cloud y service-agnostic:

  
    
    
  • Multi-nube: una sola configuración puede declarar recursos en AWS y en Azure a la vez y conectarlos con referencias, por ejemplo un registro DNS de Cloudflare que apunta a una IP de AWS. Un equipo aprende una herramienta en lugar de CloudFormation, ARM/Bicep y Deployment Manager por separado.
    • 
    
  • Nube híbrida: hay providers para lo que vive en tu centro de datos (vSphere, Proxmox, Nutanix, equipos de red, Kubernetes on-premise), así que lo local y lo público se gestionan con el mismo código y el mismo state.
    • 
    
  • Agnóstico de servicio: no solo infraestructura. Hay providers para GitHub, Datadog, PagerDuty, Okta, Vault o Cloudflare. Un repositorio puede crear la red, el clúster, el repositorio de código, los permisos y las alertas.
    • 
  

  
Ojo con la idea equivocada de que Terraform hace tu código portable entre nubes: un aws_instance no se convierte en una máquina de Azure. Lo que se comparte es el flujo, el lenguaje, el state y los módulos; los recursos de cada nube siguen siendo distintos.

  
Ventajas de la IaC que el examen da por sabidas: versionado y revisión en git, reproducibilidad (mismos entornos cada vez), automatización (menos errores manuales y más velocidad), documentación viva (el código describe lo que existe), reutilización con módulos y planes previos que muestran el impacto antes de aplicar.

Estructura de un proyecto y qué va a git

  
Terraform carga todos los ficheros .tf del directorio como si fueran uno solo. Los nombres de fichero son convención, no reglas. Esta es la convención más extendida:


mi-proyecto/
├── versions.tf          # bloque terraform {}: versión y required_providers
├── providers.tf         # configuración de cada provider
├── main.tf              # recursos
├── variables.tf         # variables de entrada
├── outputs.tf           # valores de salida
├── terraform.tfvars     # valores de las variables (cuidado con secretos)
├── .terraform.lock.hcl  # versiones exactas de providers: SÍ va a git
└── .terraform/          # plugins descargados: NO va a git

Providers y versiones


  

    

      
RestricciónPermiteUso

      
        
= 6.2.0Solo esa versiónRaro; congela demasiado

        
>= 6.0Cualquier versión desde 6.0, incluida 7, 8…Arriesgado en providers

        
~> 6.0>= 6.0 y < 7.0Lo habitual: acepta mejoras, no cambios mayores

        
~> 6.2.0>= 6.2.0 y < 6.3.0Solo parches

      
    

  

  
La restricción dice qué versiones aceptas; el fichero .terraform.lock.hcl registra cuál se eligió exactamente (con sus hashes). Por eso se commitea: todo el equipo y el CI usan los mismos binarios. Para subir de versión, terraform init -upgrade y revisa el changelog del provider.


  
Recursos: argumentos y atributos

  
Un recurso tiene una dirección única: TIPO.NOMBRE, por ejemplo aws_s3_bucket.logs. El tipo empieza siempre por el nombre del provider (aws_, docker_, github_).

  
    
    
  • Argumentos son lo que tú escribes: bucket = "acme-logs".
    • 
    
  • Atributos son lo que puedes leer después: aws_s3_bucket.logs.arn. Incluyen los argumentos y los valores que calcula la plataforma.
    • 
  

  
Cada página de recurso en el Registry tiene la misma estructura: Example Usage (copia de aquí), Argument Reference (qué puedes configurar, cuáles son obligatorios), Attribute Reference (qué puedes leer) e Import (cómo adoptar uno existente). Leerla bien es la mitad del trabajo con Terraform.


  
Data sources: leer lo que ya existe

  
Un data consulta algo que no gestiona esta configuración: la AMI más reciente, una VPC creada por otro equipo, la cuenta actual. Nunca crea ni borra nada.



  
Dependencias y el grafo

  
Terraform no ejecuta los recursos en el orden en que aparecen en el fichero. Construye un grafo dirigido a partir de las referencias: si la subred usa aws_vpc.main.id, la VPC va antes. Todo lo que no depende entre sí se crea en paralelo (10 operaciones a la vez por defecto, ajustable con -parallelism=N). Al destruir, el orden se invierte.

        Llamar a módulos

        Qué hace bueno a un módulo
        
  
          
    
        • Representa un concepto (una red, un servicio web, una base de datos con sus backups), no un único recurso. Un módulo que envuelve un solo aws_s3_bucket y reexpone todos sus argumentos solo añade una capa.
          • 
    
        • Interfaz pequeña con defaults sensatos y description en cada variable y output.
          • 
    
        • Sin bloques provider dentro. El que llama configura los providers; el módulo solo declara required_providers. Si necesita un alias, se pasa con providers = { aws = aws.use1 }.
          • 
    
        • Versionado con tags semánticos si lo usan otros equipos. Documentación generada con terraform-docs.
          • 
    
        • Poca profundidad: módulos que llaman a módulos que llaman a módulos son muy difíciles de depurar. Dos niveles suelen bastar.
          •

        sensitive: ocultar no es proteger
        
  
          
    
        • sensitive = true en una variable o un output hace que plan, apply y terraform output muestren (sensitive value). El valor sigue en claro en el state y en los planes guardados. terraform output -raw nombre o -json lo muestran.
          • 
    
        • La marca se propaga: si un output usa un valor sensible y no lo marcas como sensitive, Terraform da error.
          • 
    
        • Los providers marcan como sensibles muchos atributos, por ejemplo la contraseña de una base de datos. Las funciones sensitive() y nonsensitive() ponen y quitan la marca a mano.

        Que el secreto no llegue al state: ephemeral y write-only
        
  
        Desde la 1.10, Terraform tiene valores ephemeral: existen mientras se ejecuta el plan o el apply y nunca se escriben ni en el plan ni en el state. Desde la 1.11, los argumentos write-only permiten pasar esos valores a un recurso sin que queden guardados. Es tema nuevo de la versión 004 del examen.
        
  
        
    
        
      
        PiezaDesdeQué hace
        
      
        
        variable "x" { ephemeral = true }1.10Entrada que no se guarda. Típica: un token para configurar un provider.
        
        
        ephemeral "tipo" "nombre" {}1.10Recurso efímero: se lee o genera en cada ejecución y no se guarda. Se referencia como ephemeral.tipo.nombre.atributo.
        
        
        output "x" { ephemeral = true }1.10Solo en módulos hijos: pasa un valor efímero al módulo padre. En el módulo raíz no se permite.
        
        
        Argumento write-only (password_wo)1.11Acepta valores efímeros. El provider lo usa y Terraform guarda null. Va con password_wo_version: incrementa el número para volver a enviar el valor.
        
        
        ephemeralasnull(), terraform.applying1.10Convertir valores efímeros en null y saber si la operación es un apply.
        
              
    
        
  
        
  
        Un valor efímero solo se puede usar donde no hay riesgo de que se guarde: configuración de un provider, argumentos write-only, locals, otros bloques ephemeral, outputs efímeros de módulos hijos y provisioners. Si lo pones en un argumento normal, Terraform da error.

        Por qué OIDC
    
        Con OIDC, la plataforma de CI emite un token firmado para cada ejecución y AWS lo cambia por credenciales temporales de un rol concreto. No hay access keys guardadas en variables del pipeline que puedan filtrarse o caducar. Usa un rol de solo lectura para los planes de pull requests y otro con permisos de escritura solo para la rama principal.

        Trampas frecuentes
        
  
        
    
        
      
        Si la pregunta dice…Recuerda
        
      
        
        sensitive = true protege el secretoSolo lo oculta en la salida. Sigue en claro en el state. Lo que no se guarda son los valores ephemeral y los argumentos write-only
        
        
        Qué comandos hacen refreshplan y apply, salvo con -refresh=false. terraform refresh está obsoleto
        
        
        terraform taintObsoleto: usa apply -replace=ADDR
        
        
        terraform import genera la configuraciónEl comando no. El bloque import con plan -generate-config-out sí
        
        
        Variables en backend o cloudNo se admiten. Usa -backend-config o variables de entorno
        
        
        version en un módulo localSolo funciona con módulos de un registry. Los locales y los de git usan la ruta o ?ref=
        
        
        Un módulo hijo lee var.x del padreImposible: el padre pasa valores como argumentos y lee los outputs del hijo con module.nombre.output
        
        
        Orden de precedencia de variablesDe menor a mayor: default → TF_VAR_ → terraform.tfvars → terraform.tfvars.json → *.auto.tfvars (orden alfabético) → -var y -var-file (el último gana)
        
        
        terraform.tfvars hay que pasarlo con -var-fileSe carga solo. También *.auto.tfvars. Otros nombres sí necesitan -var-file
        
        
        ~> 1.2 frente a ~> 1.2.0~> 1.2 admite cualquier 1.x desde la 1.2. ~> 1.2.0 solo admite 1.2.x
        
        
        Workspaces de CLI = workspaces de HCPNo. En la CLI son varios states de la misma configuración; en HCP son unidades independientes con state, variables y permisos propios
        
        
        Los bloques check bloquean el applyNo: solo avisan. precondition, postcondition y validation sí detienen la operación
        
        
        TF_LOG_PATH activa los logsSolo con TF_LOG definido
        
        
        terraform destroy borra todo lo de la cuentaSolo lo que está en el state del directorio y workspace actuales
        
        
        Políticas de Sentinel u OPASe evalúan después del plan y antes del apply
        
        
        terraform validate se conecta a la nubeNo: solo comprueba sintaxis y coherencia interna. Necesita init antes para tener los providers

          Glosario
          
  
          
    
          Provider
          Plugin que traduce recursos de Terraform a llamadas a la API de una plataforma.
          
    
          Resource
          Objeto que Terraform crea y gestiona: una instancia, un bucket, un registro DNS.
          
    
          Data source
          Consulta de solo lectura sobre algo que existe fuera de esta configuración.
          
    
          State
          Registro que relaciona cada dirección del código con su objeto real y sus atributos.
          
    
          Backend
          Dónde se guarda el state y cómo se bloquea.
          
    
          Plan
          Lista de acciones que Terraform propone para que la realidad coincida con el código.
          
    
          Drift
          Diferencia entre la realidad y el state provocada por cambios fuera de Terraform.
          
    
          Module
          Carpeta de ficheros .tf con variables de entrada y outputs. El directorio donde ejecutas es el módulo raíz.
          
    
          Address
          Nombre único de un recurso: module.network.aws_subnet.public["eu-west-1a"].
          
    
          Lock file
          .terraform.lock.hcl: versiones y hashes exactos de los providers elegidos.
          
    
          Workspace (CLI)
          Varios states para la misma configuración y el mismo backend.
          
    
          Workspace (HCP)
          Unidad de HCP Terraform con su propio state, variables, permisos e historial de ejecuciones.
          
    
          HCP Terraform
          Plataforma SaaS de HashiCorp (antes Terraform Cloud) para state, ejecuciones, variables, equipos y políticas. Terraform Enterprise es su versión autoalojada.
          
    
          Project
          Grupo de workspaces de HCP Terraform con permisos y variable sets comunes.
          
    
          Variable set
          Conjunto de variables de HCP Terraform que se aplica a varios workspaces o proyectos.
          
    
          Run trigger
          Regla que lanza una ejecución en un workspace cuando otro termina un apply.
          
    
          Sentinel / OPA
          Lenguajes de policy as code que HCP Terraform evalúa entre el plan y el apply.
          
    
          Speculative plan
          Plan de solo lectura, por ejemplo en un pull request, que no se puede aplicar.
          
    
          Ephemeral
          Valor que existe durante la ejecución y nunca se guarda en el plan ni en el state.
          
    
          Write-only
          Argumento (*_wo) que acepta valores efímeros y que Terraform guarda como null.
          
    
          Backend local
          El backend por defecto: state en terraform.tfstate del directorio, con lock del sistema operativo.
          
    
          Idempotencia
          Aplicar lo mismo varias veces da el mismo resultado: sin cambios si ya coincide.
          
    
          Tainted
          Recurso marcado para reemplazo, por ejemplo porque falló su creación.
          
    
          HCL
          HashiCorp Configuration Language, el lenguaje de los ficheros .tf.
