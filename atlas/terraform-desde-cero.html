Qué es la infraestructura como código y qué hace Terraform

    •

    •

El problema: infraestructura hecha a mano

  
Imagina que montas un entorno en la consola de AWS: una red, dos subredes, un balanceador, tres servidores y una base de datos. Funciona. Seis meses después te piden un entorno idéntico para pruebas. Nadie recuerda qué casillas se marcaron, qué puerto se abrió “un momento” para depurar ni por qué la base de datos tiene ese tamaño.

  
    
    
  • No es reproducible: cada entorno se parece al anterior, pero no es igual.
    • 
    
  • No hay historial: no sabes quién cambió qué, cuándo ni por qué.
    • 
    
  • No hay revisión: un cambio en producción no pasa por ningún pull request.
    • 
    
  • Deriva: la realidad se aleja de la documentación desde el primer día.
    • 
  


  
La solución: describir la infraestructura en ficheros

  
Infraestructura como código (IaC) significa que la infraestructura se define en ficheros de texto que viven en git, se revisan en pull requests y se aplican con una herramienta. Terraform es la herramienta de IaC más usada para esto, y funciona con casi cualquier plataforma que tenga API: AWS, Azure, Google Cloud, Kubernetes, GitHub, Cloudflare, Datadog y miles más.

  

    


    

    


    

  

  
Esta es la idea central de todo el curso. En un enfoque imperativo escribes los pasos. En uno declarativo escribes el estado final que quieres, y la herramienta calcula los pasos necesarios para llegar desde donde estás. Por eso Terraform es idempotente: si la realidad ya coincide con el código, no hace nada.


  
Cómo funciona Terraform por dentro

  

    
  

  
    
    
  • Terraform Core es el binario terraform. Lee tus ficheros, construye un grafo de dependencias, compara lo que quieres con lo que existe y decide qué crear, cambiar o borrar. No sabe nada de AWS ni de Azure.
    • 
    
  • Providers son plugins que traducen recursos a llamadas de API. hashicorp/aws sabe crear una instancia EC2; integrations/github sabe crear un repositorio. Se descargan del Terraform Registry.
    • 
    
  • State es un fichero JSON donde Terraform apunta qué objeto real corresponde a cada recurso de tu código (por ejemplo, que aws_instance.web es i-0b7d4e19a2). Sin él, Terraform no sabría qué gestiona. Tiene un bloque entero dedicado (07).
    •

Licencia y OpenTofu
    
Desde agosto de 2023 (versión 1.6), Terraform se publica con la licencia Business Source License 1.1. Para usarlo en tu empresa para gestionar vuestra propia infraestructura no cambia nada; la restricción afecta a quien vende productos que compiten con HashiCorp. Estructura de un proyecto y qué va a git

  
Terraform carga todos los ficheros .tf del directorio como si fueran uno solo. Los nombres de fichero son convención, no reglas. Esta es la convención más extendida:


mi-proyecto/
├── versions.tf          # bloque terraform {}: versión y required_providers
├── providers.tf         # configuración de cada provider
├── main.tf              # recursos
├── variables.tf         # variables de entrada
├── outputs.tf           # valores de salida
├── terraform.tfvars     # valores de las variables (cuidado con secretos)
├── .terraform.lock.hcl  # versiones exactas de providers: SÍ va a git
└── .terraform/          # plugins descargados: NO va a git

Interactivo

  ami           = "ami-0abc123"

La forma general de todo HCL es siempre la misma: TIPO "etiqueta" "etiqueta" { argumento = valor }. El número de etiquetas depende del tipo de bloque: resource lleva dos, variable una y locals ninguna.

ComandoQué haceCuándo

Cómo leer un plan

  

    

      
SímboloSignificadoRiesgo

      
        
+Se crearáBajo

        
~Se actualizará en el sitio (mismo objeto, mismo ID)Medio: revisa qué cambia

        
-Se destruiráAlto: confirma que es intencionado

        
-/+Se destruirá y se creará uno nuevo (reemplazo). Busca el comentario # forces replacementAlto: pérdida de datos o corte de servicio

        
+/-Se creará el nuevo y después se destruirá el viejo (create_before_destroy)Medio

        
<=Un data source se leerá durante el applyNinguno

      
    

  


  
(known after apply) significa que el valor lo decide la plataforma al crear el objeto (un ID, una IP, un ARN). Lee siempre la última línea primero: si esperabas “1 to change” y ves “3 to destroy”, para y averigua por qué.


  
Aplica exactamente lo que revisaste

Providers y versiones


  

    

      
RestricciónPermiteUso

      
        
= 6.2.0Solo esa versiónRaro; congela demasiado

        
>= 6.0Cualquier versión desde 6.0, incluida 7, 8…Arriesgado en providers

        
~> 6.0>= 6.0 y < 7.0Lo habitual: acepta mejoras, no cambios mayores

        
~> 6.2.0>= 6.2.0 y < 6.3.0Solo parches

      
    

  

  
La restricción dice qué versiones aceptas; el fichero .terraform.lock.hcl registra cuál se eligió exactamente (con sus hashes). Por eso se commitea: todo el equipo y el CI usan los mismos binarios. Para subir de versión, terraform init -upgrade y revisa el changelog del provider.


  
Recursos: argumentos y atributos

  
Un recurso tiene una dirección única: TIPO.NOMBRE, por ejemplo aws_s3_bucket.logs. El tipo empieza siempre por el nombre del provider (aws_, docker_, github_).

  
    
    
  • Argumentos son lo que tú escribes: bucket = "acme-logs".
    • 
    
  • Atributos son lo que puedes leer después: aws_s3_bucket.logs.arn. Incluyen los argumentos y los valores que calcula la plataforma.
    • 
  

  
Cada página de recurso en el Registry tiene la misma estructura: Example Usage (copia de aquí), Argument Reference (qué puedes configurar, cuáles son obligatorios), Attribute Reference (qué puedes leer) e Import (cómo adoptar uno existente). Leerla bien es la mitad del trabajo con Terraform.


  
Data sources: leer lo que ya existe

  
Un data consulta algo que no gestiona esta configuración: la AMI más reciente, una VPC creada por otro equipo, la cuenta actual. Nunca crea ni borra nada.



  
Dependencias y el grafo

  
Terraform no ejecuta los recursos en el orden en que aparecen en el fichero. Construye un grafo dirigido a partir de las referencias: si la subred usa aws_vpc.main.id, la VPC va antes. Todo lo que no depende entre sí se crea en paralelo (10 operaciones a la vez por defecto, ajustable con -parallelism=N). Al destruir, el orden se invierte.

Variables, outputs y locals

  
Las variables son las entradas de tu configuración, los outputs sus salidas y los locals sus cálculos internos. Juntos convierten un ejemplo fijo en código reutilizable.

  
Al terminar sabrás

Variables de entrada


  
Una variable sin default es obligatoria: si nadie le da valor, Terraform la pide por teclado (o falla con -input=false, como en CI). Escribe siempre description y type: son la documentación de tu módulo.


  
Cómo se asignan los valores y cuál gana

  

    
Interactivo
Precedencia de variables

    
Activa y desactiva fuentes. Están ordenadas de menor a mayor prioridad: la última activa gana.

    
    
    
    
  
    


  
    Locals: cálculos internos
    

  
    Regla práctica: si un valor lo decide quien usa el código, es una variable. Si se deriva de otros valores o se repite, es un local. No conviertas en variable algo que nunca va a cambiar.
    

  
    Outputs
    


  
    Los outputs tienen dos usos: mostrar información tras el apply y, sobre todo, pasar valores de un módulo a otro (bloque 10).
    
  
    sensitive no cifra nada
    
    sensitive = true solo oculta el valor en la salida de plan y apply ((sensitive value)). El valor se guarda en claro en el state. La protección real es cifrar y restringir el acceso al state (bloque 11). Desde la versión 1.10 existen valores ephemeral y, desde la 1.11, argumentos write-only en algunos recursos, que evitan que ciertos secretos lleguen al state.

        La idea
        
  
        Un módulo funciona como una función: recibe variables, crea recursos por dentro y devuelve outputs. Desde fuera solo se ve esa interfaz.
        
  
        
    
  
        

  
        Escribir un módulo
        

        infra/
├── modules/
│   └── network/
│       ├── main.tf        # recursos
│       ├── variables.tf   # interfaz de entrada
│       ├── outputs.tf     # interfaz de salida
│       ├── versions.tf    # required_providers, sin bloque provider
│       └── README.md
└── envs/
    └── dev/
        └── main.tf        # llama a ../../modules/network
        




  
        Llamar a módulos
        

  
        Después de añadir o cambiar el source de un módulo, ejecuta terraform init para descargarlo. Las direcciones dentro de un módulo llevan prefijo: module.network.aws_vpc.this. Para mover recursos existentes a un módulo sin destruirlos, usa un bloque moved (bloque 07).
        

  
        Qué hace bueno a un módulo
        
  
          
    
        • Representa un concepto (una red, un servicio web, una base de datos con sus backups), no un único recurso. Un módulo que envuelve un solo aws_s3_bucket y reexpone todos sus argumentos solo añade una capa.
          • 
    
        • Interfaz pequeña con defaults sensatos y description en cada variable y output.
          • 
    
        • Sin bloques provider dentro. El que llama configura los providers; el módulo solo declara required_providers. Si necesita un alias, se pasa con providers = { aws = aws.use1 }.
          • 
    
        • Versionado con tags semánticos si lo usan otros equipos. Documentación generada con terraform-docs.
          • 
    
        • Poca profundidad: módulos que llaman a módulos que llaman a módulos son muy difíciles de depurar. Dos niveles suelen bastar.
          • 
  
        
  
        Antes de escribir uno, busca en el Registry de módulos. Los de terraform-aws-modules son muy usados y una buena referencia de estilo, aunque leerlos enteros cuesta: son genéricos a propósito.

        Por qué OIDC
    
        Con OIDC, la plataforma de CI emite un token firmado para cada ejecución y AWS lo cambia por credenciales temporales de un rol concreto. No hay access keys guardadas en variables del pipeline que puedan filtrarse o caducar. Usa un rol de solo lectura para los planes de pull requests y otro con permisos de escritura solo para la rama principal.
        
  
        

  
        Plataformas especializadas
        
  
        Si no quieres montar el flujo a mano: Atlantis (open source, comenta el plan en el PR y aplica con un comentario atlantis apply), HCP Terraform (state, ejecuciones, políticas y registro privado de HashiCorp), y alternativas como Spacelift, env0 o Scalr.
        

  
        Prácticas de equipo
        
  
          
    
        • Nada de cambios en la consola en entornos gestionados. Si hay emergencia, después se refleja en el código.
          • 
    
        • States pequeños por entorno y capa: limitan el radio de impacto de cada error.
          • 
    
        • Versiones fijadas: Terraform (required_version y .terraform-version), providers (lock file commiteado) y módulos (version o ref).
          • 
    
        • Planes legibles en el PR y revisión obligatoria cuando hay - o -/+.
          • 
    
        • Detección de drift con un plan programado que avise si el resultado no es “No changes”. terraform plan -detailed-exitcode devuelve 2 cuando hay cambios.
          • 
    
        • Convención de etiquetas (default_tags) para saber de quién es cada recurso y cuánto cuesta.
          • 
  
        

  
        
  
        
    
        Practica
        
    
          
      
        1. Crea en AWS el proveedor de identidad OIDC de tu plataforma de CI y un rol con confianza limitada a tu repositorio.
          2. 
      
        2. Monta el pipeline de tu plataforma: plan en cada PR y apply manual en main.
          3. 
      
        3. Añade un pipeline programado que ejecute terraform plan -detailed-exitcode y falle si el código de salida es 2.
          4.

        Proyecto final: una web en AWS de principio a fin
        
  
        Junta todo lo aprendido en un repositorio que podrías enseñar en una entrevista: red, servidores, dos entornos, state remoto, tests y pipeline. Marca cada tarea al terminarla; se guarda en este navegador.
        

        tf-web/
├── bootstrap/                 # bucket del state (state local)
├── modules/
│   ├── network/               # VPC, 2 subredes públicas, IGW, rutas
│   └── web/                   # SG dinámico, instancias, user_data con templatefile
├── envs/
│   ├── dev/                   # backend propio, t3.micro, 1 instancia
│   └── prod/                  # backend propio, 2 instancias, prevent_destroy
├── tests/                     # terraform test con mock_provider
├── .pre-commit-config.yaml
├── .tflint.hcl
├── .terraform-version
└── bitbucket-pipelines.yml    # o .github/workflows/terraform.yml

        Glosario
        
  
        
    
        Provider
        Plugin que traduce recursos de Terraform a llamadas a la API de una plataforma.
        
    
        Resource
        Objeto que Terraform crea y gestiona: una instancia, un bucket, un registro DNS.
        
    
        Data source
        Consulta de solo lectura sobre algo que existe fuera de esta configuración.
        
    
        State
        Registro que relaciona cada dirección del código con su objeto real y sus atributos.
        
    
        Backend
        Dónde se guarda el state y cómo se bloquea.
        
    
        Plan
        Lista de acciones que Terraform propone para que la realidad coincida con el código.
        
    
        Drift
        Diferencia entre la realidad y el state provocada por cambios fuera de Terraform.
        
    
        Module
        Carpeta de ficheros .tf con variables de entrada y outputs. El directorio donde ejecutas es el módulo raíz.
        
    
        Address
        Nombre único de un recurso: module.network.aws_subnet.public["eu-west-1a"].
        
    
        Lock file
        .terraform.lock.hcl: versiones y hashes exactos de los providers elegidos.
        
    
        Workspace
        Varios states para la misma configuración y el mismo backend.
        
    
        Idempotencia
        Aplicar lo mismo varias veces da el mismo resultado: sin cambios si ya coincide.
        
    
        Tainted
        Recurso marcado para reemplazo, por ejemplo porque falló su creación.
        
    
        HCL
        HashiCorp Configuration Language, el lenguaje de los ficheros .tf.
        
  
        
  
        Guía escrita para Terraform 1.x. Las versiones mínimas citadas (1.5 para import, 1.10 para use_lockfile, etc.) indican desde cuándo existe cada función. Ante la duda, la documentación oficial manda.
